# 用户端全流程构建问题汇总与前后端优化方案

**日期**: 2026-09-13
**来源**: 真实用户测试 — 通过浏览器实际操作 Web 界面，从零构建一台"四舵轮 Quad Steer AGV"（4000×2000×500mm，双激光导航，4灯带，5按钮，1电池，1个RS485显示屏，步科CANopen驱动），全程走完 5 步向导（身份信息 → 底盘与动力 → 装备工坊 → 功能映射 → 审计导出）并导出 `.cmodel`
**对象**: `amr.cloud-ai.work` 部署版本（Frontend v1.0.0，Backend v1.0.1-worker-ts / worker-ts-edge）
**测试方式**: 全程真实 UI 操作（点击、输入、滚动），未使用任何 API 捷径；仅在诊断阶段用 JS 辅助定位被 UI bug 卡住的元素

---

## 一、测试过程概述

本次测试完整走完了新建项目 → 底盘尺寸/动力学参数 → 4个轮组(每组含左右驱动器+左右电机+编码器) → 传感器/电池/按钮/屏幕/灯光装配 → 电气接口参数配置 → 功能能力映射 → 审计校验 → 编译导出的全链路。过程中发现的问题大致分三类：

1. **前端交互 bug**（可复现、影响操作但不影响数据模型正确性）
2. **前端数据持久化 bug**（严重，会静默丢失用户输入）
3. **目录/模板数据缺口**（后端/数据层面，导致部分需求在当前系统里物理上无法配置）

以下按严重程度排列。

## 二、前端问题清单

### 问题 1（严重）：接口参数字段未真正持久化，且无任何报错提示

**反馈**：在"电气连接"步骤为激光雷达的 `ETH_1` 接口填写 IP 地址（如 `192.168.1.11`），输入后按 `Tab` 键切换焦点，界面显示正常、"参数完整度"列也从"缺失"变为"完整"。但保存项目、刷新页面并重新载入后，该字段又变回空值，"参数完整度"打回"缺失"。

**具体表现**：
- 用 `Tab` 键失焦 → 视觉上"成功"，但底层 state 未提交
- 用鼠标点击页面其他区域失焦 → 才会真正提交并在刷新后保持

**根因推测**：接口参数输入框（`SmartForm` 或 `WiringStep.tsx` 中对应的 `<Input>`）的提交时机绑定在 `onBlur`，但 `Tab` 触发的 blur 事件可能被父级容器（如 Ant Design 的 Card/虚拟滚动容器）的 `onKeyDown` 拦截提前阻止了冒泡，或者 `onBlur` handler 里有一个异步的 setState 竞态，被后续的路由/tab切换打断而没有真正写入 `useProjectStore`。整个过程中前端没有任何 loading/toast 反馈，用户完全不会意识到数据丢失。

**解决方案**：
1. 把提交时机从 `onBlur` 改为 `onChange` 防抖（如 300ms debounce）直接写入 store，不依赖失焦事件，从根本上消除这一类"看起来保存了、实际没保存"的问题。
2. 在 `useProjectStore` 的 `updateAttribute` / 接口参数更新方法中加入开发环境下的写入日志，便于后续同类问题快速定位。
3. 保存成功后，"参数完整度"这类派生状态应该直接从 store 里的当前值重新计算展示，而不是保留一份"刚才操作成功"的乐观 UI 状态；这样只要展示层没有回退，就能保证展示的和实际保存的一致。

### 问题 2（严重）：部分文本输入框 Backspace / Delete 键位不生效

**反馈**：在配置驱动器"芯片平台"字段时，多次输入后出现新旧文本拼接、乱码（例如打算清空重填却得到 `"StepStepko"` `"epkStepko"` 等结果）。测试确认：单独按字符键可以正常插入，但按 `Backspace`/`Delete` 键，或先 `Ctrl+A` 全选再删除，均对该输入框无效。

**根因推测**：该输入框很可能是一个受控组件，其 `onKeyDown` 或 `onChange` 里存在自定义逻辑（例如某种输入格式化/过滤器）意外拦截并 `preventDefault()` 了删除类按键，但没有对应处理这些按键应有的删除效果，导致按键被"吃掉"但没有产生任何变化。

**解决方案**：
1. 排查该输入框组件是否有自定义 `onKeyDown`，如果只是想限制输入字符集（比如型号只允许字母数字），应该在 `onChange` 里做正则过滤，而不是在 `onKeyDown` 里拦截按键。
2. 增加针对文本输入框的自动化回归测试：模拟"输入→全选→删除→重新输入"序列，断言最终值等于最后一次输入，防止此类问题再次引入。

---

### 问题 3（中等）：虚拟滚动树中的节点在长列表下完全无法通过常规方式选中

**反馈**：在装备工坊/动力组成的组件树中（尤其是电机、驱动器较多时，本次构建有 4 组 × 6 个子节点共 24 个树节点），部分节点会被渲染在可视区域之外几千像素的位置。此时无论是直接点击、双击、键盘方向键导航，还是重新调整窗口大小、刷新整个页面，都无法选中该节点，界面停留在此前选中的节点不动。

**根因确认**：通过检查 DOM 发现，问题节点的 `getBoundingClientRect().y` 值可达 5000+，而 `window.scrollY` 只有 1000 左右——说明该树使用了虚拟滚动（windowed list），但树自身内部滚动容器的位置和外部页面滚动状态不同步。只有直接对该 DOM 节点调用 `scrollIntoView()` 才能让虚拟列表重新计算并渲染出目标节点，常规的“滚动页面到某坐标再点击”完全无法触发虚拟列表的内部滚动。

**解决方案**：
1. 检查该 Ant Design `Tree` 组件的 `height`/`virtual` 配置，确认是否所有需要长期支持"跳转到某节点"的场景（比如新增组件后自动定位到新节点、审计报错后自动跳转到问题组件）都通过 `treeRef.current.scrollTo({ key })` 这类官方 API 触发，而不是依赖外部的 `window.scrollTo` 或第三方 UI 自动化工具的坐标点击。
2. 对于组件数量不多（本项目量级在几十到一百多个）的场景，可以考虑关闭虚拟滚动（`virtual={false}`），用换取的少量渲染性能开销来彻底避免这一类可达性问题；只有在组件数达到几百个以上时虚拟滚动的收益才明显。

### 问题 4（中等）：下拉框选中后收起状态文字不及时刷新

**反馈**：选择"驱动类型"下拉框中的选项后，收起状态显示的文字有时不会立即更新为新选中值，需要重新展开下拉框才能看到确实已经选中。

**解决方案**：检查该 Select 是否使用了 `value` + `onChange` 的受控模式；如果 `value` 来自 store 而更新 store 的 setState 和关闭下拉框的动画在同一个事件循环里存在竞态，可以把 `onChange` 里的 store 更新提前到下拉框关闭动画开始之前，或直接用 `key` 强制在值变化时重渲染该 Select。

---

### 问题 5（中等）：装配位置意图解算为 (0,0,0) 时，无法被标记为"已定位"

**反馈**：新装配一个组件后，如果选择的安装位置意图（如"中心"）刚好解算出坐标 (0,0,0)，即使点击保存按钮，组件状态也不会从"待定位"变为"已定位"。必须选择一个能让某个坐标轴变为非零值的位置意图（如"顶部"）才能被系统识别为确认定位。整个过程没有任何提示文字。

**根因推测**：判定"已定位"的逻辑很可能是用 `x !== 0 || y !== 0 || z !== 0` 这类"坐标非零即视为已设置"的启发式判断，而不是一个独立的、显式的 `isPositioned: boolean` 标志位。这在坐标恰好合法地为原点时会产生误判。

**解决方案**：为每个组件的位姿数据单独增加一个显式的 `poseConfirmed`/`isPositioned` 布尔字段，由用户点击"装配到车辆"/"保存结构关系与位姿"按钮时显式置位，完全不依赖坐标数值本身，从根源上消除这类"合法值被误判为未设置"的问题。这个模式也应该同样应用在其他"数值默认为0是否等于未填写"的判断上（比如审计里对必填数值字段的校验，应检查字段是否存在，而不是检查是否等于0）。

---

### 问题 6（严重）：电气连接页面的接线表单被模块库选型面板持续遮挡

**反馈**：只要在"结构装配"步骤点击过任意一个"功能装备栏"类目进行筛选，切换到"电气连接"步骤后，"模块库"选型面板会持续渲染在"电气连接·从能看见到能通信"接线表单（源模块/源接口/目标模块/目标接口/建立连接）的同一区域，将其完全遮挡。刷新整个页面、重新进入该步骤均无法消除遮挡，只能通过直接操作被遮挡元素的底层 DOM 才能继续使用该表单。

**根因推测**：这两个卡片组件大概率共享了同一个"当前选中类目"或"面板展开"状态（比如都读同一个 `selectedCategory` 或 `activePanel` 全局 state），"模块库"面板的显示条件很可能是"只要 selectedCategory 不为空就渲染"，而没有区分当前所处的是"结构装配"步骤还是"电气连接"步骤，导致状态从上一个步骤"泄漏"到了下一个步骤。

**解决方案**：
1. 将"模块库"选型面板的显示状态从全局/跨步骤共享的 store 中拆分出来，改为仅在"结构装配"（`ComponentLibraryStep` / `MountingStep`）步骤内部的局部 state，离开该步骤时自动重置/卸载。
2. 补充一条端到端测试：进入结构装配步骤 → 点击任意类目 → 切换到电气连接步骤 → 断言模块库面板不可见。这是一个纯 UI 回归问题，用一个简单的 Playwright/Cypress 用例即可长期防止再犯。

### 问题 7（严重）：编译导出按钮稳定报错，但同一后端接口直接调用其实成功

**反馈**：在"审计导出"步骤点击"完成并云端编译"按钮，稳定复现如下报错弹窗：
```
构建失败: A Worker script configured by the website owner threw an unhandled exception while processing this request.
```
但对同一项目直接发起 `POST /api/v1/models/{project_id}/compile` 请求（不带任何特殊 body），实际返回 `200`：
```json
{
  "status": "success",
  "project_id": "new_proj_ito63ug",
  "runtime": "cloudflare-worker-typescript",
  "download_url": "/api/v1/models/new_proj_ito63ug/artifacts/new_proj_ito63ug_packed.cmodel",
  "audit": ["CompDesc.model built by Worker TS: 59857 bytes", "AbiSet.model built by Worker TS: 1090 bytes"]
}
```
并且该 `download_url` 可以正常下载出一个结构完整（`CompDesc.model` + `AbiSet.model` + `ModelFileDesc.json` 的 zip 包）、大小 9438 字节的 `.cmodel` 文件。

**根因推测**：这不是后端编译能力本身的问题，而是前端按钮点击处理函数在发起编译请求之前/之后做了某些额外操作（例如先做一次全量配置同步 PATCH、或者在请求体里附带了某个当前状态下不合法的字段）导致 Worker 在处理该请求时抛出未捕获异常。已观察到的一个旁证：在同一次网络请求记录里，紧邻 compile 调用前后的一批组件 `PATCH` 请求中，有一条返回了 `500`（`.../components/9923bc16-... → 500`），提示前端在编译前的批量同步阶段本身就存在偶发失败，而按钮的编译处理逻辑很可能没有正确处理"同步阶段部分组件失败"这种情况，进而带着不完整/不一致的状态去调用 compile，或是在同步失败后仍然继续、把错误状态一并抛给了 Worker。

**解决方案**：
1. **前端**：给"完成并云端编译"按钮的点击处理函数补充清晰的分步骤日志/状态展示（"1/2 同步配置中" → "2/2 编译中"），并且在同步阶段任何一个 PATCH 失败时立即中止并给用户明确的错误信息，而不是静默继续到编译阶段。
2. **前端**：捕获 compile 请求的失败响应体（而不是把 Cloudflare Worker 的原始异常文本直接展示给终端用户），转换成对用户友好的中文提示，技术细节写入前端错误日志/上报系统。
3. **后端**：给 `compile` 这个 Worker 入口加上顶层 `try/catch`，任何未捕获异常都应该被转换成结构化的 JSON 错误响应（带错误码和可读信息），而不是让运行时抛出裸的"unhandled exception"文本直接透传给客户端——这是一个可以独立于前端 bug、优先修复的后端健壮性问题。
4. 补充一个针对"编译流程"的集成测试：模拟同步阶段某个组件 PATCH 失败的情况，断言前端能正确阻止/提示，而不是带着脏状态继续调用 compile。

### 问题 8（轻微）："导出配置"按钮的实际行为与其名称不符

**反馈**：顶部导航区域的"导出配置"按钮点击后，界面提示"正在同步配置..."，实测并不会触发任何文件下载，其行为更像是把当前项目同步/保存到服务器，而不是导出一个文件。

**解决方案**：将该按钮重命名为"同步配置"或"保存到云端"，避免与"审计导出"步骤里真正产出 `.cmodel` 文件的"完成并云端编译"功能混淆。

## 三、后端 / 数据（模块目录 & Schema）问题清单

以下问题无法通过前端交互解决，需要后端/数据团队补充模板库或调整 schema 定义：

### 问题 9（严重）：模块目录中不存在任何"主控制器"产品

"主控与通信"类目下目录数量为 0，仅有 `covers-Common`、`通用覆盖件` 等 `AUTOBODY`/`UNKNOWN` 类型的占位覆盖件产品，没有任何主控制器/VCU 类型的真实产品。这直接导致"一台车必须具备一个主控制器"这条业务规则在当前系统里对任何用户都无法真正落地。

**解决方案**：在 `resources/modules/` 目录下补充至少一款真实的主控制器模板（`mainModuleType` 应归入一个专门的 `MainController`/`VCU` 类型，而不是复用 `AUTOBODY`/`covers` 这类占位类型），并在其 `interfaceAbility` 中声明足够数量的 CAN/以太网端口，供驱动器和 IO 模块挂载。

### 问题 10（严重）：驱动器 / 电机 / 编码器组件模板不包含任何电气接口定义

在"电气连接"页面和独立的接线表单中反复验证：任选一个差速舵轮组的驱动器作为"源模块"，其"源接口"下拉框返回 "No data"。也就是说驱动器组件的模板里根本没有定义 CAN 接口字段。这意味着即使补上了问题 9 的主控制器，"驱动器通过 CAN2 用 CANopen 协议连接主控"这条业务规则依然无法在系统里连线——因为驱动器一侧压根没有可选的接口。

**解决方案**：为驱动器（`DRIVER`）类型组件的模板补充 `interfaceAbility`/`interfaceParams`，至少包含一个 CAN 接口（协议标注为 CANopen），字段结构可参照现有 IO 模块模板里 CAN_1 接口的定义方式（波特率、nodeId）。

### 问题 11（中等）：IO 扩展模块规格与常见业务需求（8进10出）不匹配

目录里最接近的产品是"IO module 4in4out"（4 输入 / 4 输出），比常见的"8进10出"规格小。但该产品装配后的接口详情显示其物理接口总数为 10（1×PI + 1×CAN + 4×DI + 4×DO），说明产品命名口径和实际物理接口清单存在不一致，容易让用户误判该产品的实际 IO 能力。

**解决方案**：补充一款 8DI/10DO 规格的 IO 模块模板；同时建议在产品命名和展示上，把"型号名称里的 in/out 数字"和"详情面板里展示的物理接口清单"做一次口径核对，确保两者含义一致（比如是否都只统计 DI/DO，还是把 CAN/PI 也计入"接口"总数）。

### 问题 12（中等）：缺少可配置的"灯带"类产品，仅有单点警示灯

"声光与人机"类目下的光源类产品只有一款单点示宽警示灯（`指示灯,L5-63T01`），没有可配置长度/分段、支持连续发光效果的"灯带"类型产品。当业务需求是"4个灯带"时，只能靠重复装配 4 次同一款单点灯来近似模拟，实际物理形态和真实灯带有本质差异。

**解决方案**：补充至少一款真正的灯带类产品模板，允许配置长度、颜色分段数等参数。

### 问题 13（中等）：缺少防撞条产品，导致"急停"功能的关联防撞条字段永远无法绑定

"急停"功能映射面板里的"关联防撞条"字段，在整个装配清单和模块目录里都找不到任何可绑定的防撞条类组件。

**解决方案**：补充防撞条（Safety Edge / Bumper）类型的产品模板，并确保其能出现在"避障与安全"类目下。

### 问题 14（中等）：RS485 模板未定义 stationId（站号）字段

系统在电气接口矩阵页面明确提示"RS485 当前模板未定义 stationId 字段，站号规则 unresolved"。也就是说，即使补上了主控制器，RS485 总线上挂载的电池、显示屏等多个从站之间也无法通过界面区分彼此的站号——这是 schema 层面的字段缺失，不是用户没填。

**解决方案**：在 RS485 类型接口的 `interfaceParams` schema 中补充 `stationId` 字段定义，并在电气接口矩阵的参数配置面板中为该字段提供输入框（校验同一条总线内站号不重复）。

### 问题 15（轻微）：新建项目时 `componentAbility` / `FuncDesc` 恒为空

审计页面明确提示"当前前端未加载 FuncDesc 功能过程。新建项目或缺少 FuncDesc 时，需要用户或后端模板显式提供，前端不会猜测生成"，`componentAbility` 同样为空。这两项数据结构在"新建项目"这条路径上从一开始就没有被初始化。

**解决方案**：明确这两个字段的产品定位——如果它们是"必须通过导入已有 `.cmodel` 才能获得"的数据，应在新建项目向导里用一条说明文案告知用户，而不是等到审计页面才以警告形式出现；如果它们本应该有合理的默认初始值，则应该在新建项目的初始化逻辑里补上。

## 五、总结

本次全流程测试证明：装配、位姿、传感器绑定、功能映射、审计校验这条主链路是可用的，最终能够产出结构合法的 `.cmodel` 文件。真正卡住"完整还原一台工业级 AGV 电气拓扑"的，是两类问题的叠加——**前端有两个会导致数据静默丢失/流程中断的严重 bug（问题1、问题7）**，以及**数据目录里主控制器和驱动器电气接口这两项核心能力的缺失（问题9、问题10）**。建议优先解决 P0 的 4 项，它们分别覆盖了"用户输入是否真的被保存""导出流程是否稳定可用""电气拓扑闭环是否可能"这三个最基础的产品可用性问题。
