## 0. 重要纠偏说明（读者必读）

既有实操报告 `audits/20260913_用户构建流程问题汇总与前后端优化方案.md` 的"问题9"曾结论为"主控制器产品在系统中完全不存在"。本次结合代码复核，该结论**不准确，需要纠正**：

| 层级 | 数据源 | 实测内容 | 结论 |
|---|---|---|---|
| ① 类型 Schema 层 | `src/backend/resources/definitions/mainCPU.xml`（`SchemaManager` 加载，经 `GET /api/v1/schemas` 下发） | 存在 `mainCPU` moduleType，但 `subTypes` 只有 2 个**通用占位型号**（`mainCPU`=主控制器 / `mainCpu`=通用CPU），无品牌型号 | 类型定义存在，但不是"可选购的具体产品" |
| ② 品牌产品模板层 | `src/backend/resources/modules/*.json`（287 个文件，`resource_adapter.py`/`encoder.py` 序列化时用于缺省值补全） | **真实存在** `MCPU-RA-MC-R318AT.json`、`MCPU-RA-MC-R318BN.json`、`MCPU-RA-MC-R349AD-21BH0.json`、`mainCPU-Common.json`、`intergratedController-Common.json`、`safetyController-Common.json` 等具名主控/安全控制器产品 | 品牌产品模板确实存在，但目前**只在导出兜底阶段被读取**，未暴露为前端"组件库"里可浏览挑选的条目 |
| ③ 板卡规格层 | `specifications/ModuleLibrary/board_desc/host/RA-MC-R318{AT,AD,BN,CT}.json` → 聚合进 `Aggregated/BoardDescriptions.xml` → 后端 `GET /api/v1/resources/boards` 单独下发 | 存在，且已在 `api_v2.ts`/`useProjectStore.ts` 中被引用，用于组件**创建之后**根据"芯片平台"下拉框动态注入 ETH/CAN/RS485 接口 | 板卡级接口规格存在且已接入代码，但只服务于"接口自动注入"这一个用途 |

**结论**：主控制器不是"完全缺失"，而是**存在三套互不相通的数据源**，各自服务于不同的子功能（类型定义 / 导出兜底 / 接口注入），却从未被整合为用户在"组件库"第一次选型时能看到的、带品牌型号名称的产品目录。这是一个**数据编排/前端集成缺口**，而不是"内容缺失"，修复成本和方案因此完全不同（见 REQ-BE-06、《后端设计》§4、《总体设计》§5）。本文档后续所有涉及主控制器的需求条目均以此为准。

## 1. 产品范围与术语

### 1.1 范围
AMR Studio V4 是一个面向工业级自主移动机器人（AMR/AGV）整车电子电气配置的可视化建模平台。用户通过 Web 向导完成底盘定义、硬件选型、空间标定、总线接线、能力映射、审计校验，最终导出与 ModelSet312 控制器协议**位对齐（Bit-Perfect）**的 `.cmodel` 文件供下位机加载。

本次需求细化以真实交付案例为基准场景（见 §2），该场景已于 2026-09-13 通过浏览器实操完整走通并成功导出 `.cmodel`（交付物：`amr_quad_steer_4000x2000_packed.cmodel`），本规格书中标注"✅ 已验证"的需求项均以该案例的真实操作结果为证据。

### 1.2 术语（沿用仓库既有定义，不重复造词）
沿用 `CLAUDE.md`、`CONSTRAINTS.md`、`specifications/ENGINEERING_CONSTRAINTS.md` 中的既有术语：`Message_Module_Info`、`privateAttrs`/`private_attr`、`DATA_COMBOX`、`DATA_FIXED_E`、`subSysType`、`moduleSys`、18 类硬件大类（chassis/driveWheel/autobody/actor/driver/mainCPU/intergratedController/energyController/sensorProcessor/extendedlnterface/sensor/communication/battery/light/button/audio/screen/handOperator）、34 种接口类型。**开发/评审时不得另造同义词**。

## 2. 基准场景（Reference Case，用于验收本文档所有需求）

四舵轮差速转向 AGV：

## 4. 功能性需求

编号规则：`REQ-<模块>-<序号>`。每条需求给出【验收标准】与【追溯】（对应历史问题编号或代码位置）。

### 4.1 工程身份与底盘 (IDENTITY / CHASSIS)

**REQ-ID-01** 系统必须支持录入 `robotName`、`materialCode`、`navigationMethod`、`driveType`。
✅ 已验证。追溯：`IdentityStep.tsx`。

**REQ-CH-01** 底盘物理包络（长/宽/高）与运动中心偏移必须区分**空载（Idle）**与**满载（Full Load）**两组独立字段，且两组字段中的全部 6 项（`headOffset/tailOffset/leftOffset/rightOffset` × 2 状态）在导入/导出链路中不得选择性丢弃。
【验收标准】对照 `CLAUDE.md §1.2`、`CONSTRAINTS.md §2` 的 `ROBOT_IDENTITY_FIELDS`（24 字段清单）逐字段回归测试，Import→Export 往返后 24 字段全部保留。
追溯：历史缺陷 `ImportService.ts`(2026-04-05)、`ExportService`(2026-04-06)，已修复但需在本规格书中固化为**不可回归**的硬性需求，并纳入 CI 回归清单（见《开发规范》§7）。

**REQ-CH-02** 底盘空载动力学参数（最大角加速度、最大角速度）为审计 ERROR 级必填项，且新建项目时不得以 0 或空值通过。
【验收标准】新建底盘后审计页面必须在未填写前阻断导出。
追溯：本次实操中命中的真实 ERROR（修复前 5 个 ERROR 之一）。

**REQ-CH-03** 差速舵轮组的"轮间距"字段必须与轮径、限位角度一样被审计强制校验 `> 最小允许值`，且系统在批量创建多个轮组（如 4 组）时不得出现"仅第 1 组遗留默认值 0、其余组正常"的不一致继承问题。
【验收标准】新建 N（N≥2）个同类轮组后，逐组比对默认值来源，禁止"第一组特殊路径未走完整 schema 默认值填充"。
追溯：本次实操中命中的真实 ERROR（轮组1轮间距=0，其余组=600），根因怀疑与 `doCreateWheel` 首组件创建时序有关，需在《后端设计》/《前端界面设计》中给出具体修复点。

### 4.2 硬件选型与组件库 (COMPONENT LIBRARY)

**REQ-CL-01** "核心控制板"分类下，用户必须能够在**组件库选型阶段（而非仅接口注入阶段）**浏览到品牌级主控制器/安全控制器产品（如 `RA-MC-R318AT/AD/BN`、`RA-MC-R349AD-21BH0`）并直接添加为项目组件。
【验收标准】"核心控制板"子步骤列表中，选择"主控制器"过滤器后，可见条目数 ≥ `resources/modules/*.json` 中实际存在的主控/安全控制器数量（当前应 ≥ 6：3 款 RA-MC 系列 + mainCPU-Common + intergratedController-Common + safetyController-Common）。
追溯：纠正 `audits/20260913_...` 问题9；本条为**新增需求**，弥合本文档 §0 所述三层数据源的断层。是本次需求细化中优先级最高（P0）的条目。

**REQ-CL-02** IO 扩展模块目录必须提供满足 8 进 10 出（或可配置 DI/DO 数量）规格的产品条目；当前仅有"IO module 4in4out"（实测装配后物理接口数为 10：1 PI + 1 CAN + 4 DI + 4 DO）不满足命名与规格的一致性，需要新增或修正规格描述。
【验收标准】IO 扩展板分类下至少 1 款条目的 `generalAttr.moduleDesc` 与其 `interfaceParams` 中的 DI/DO 数量描述一致。
追溯：`audits/20260913_...` 问题3。

**REQ-CL-03** "声光与人机"分类下必须提供独立的"灯带"产品类型（区别于当前唯一的单点警示灯 `L5-63T01`），支持多分段/长度可配置。
追溯：`audits/20260913_...` 问题4。**优先级 P2**（当前可用同款警示灯重复装配 4 次近似满足，非阻断）。

**REQ-CL-04** 必须提供"防撞条"产品类型，并可在急停功能面板中绑定。
追溯：`audits/20260913_...` 问题5。**优先级 P2**。

**REQ-CL-05** 驱动器/电机组件模板必须包含 CAN 接口定义字段（当前"建立连接"表单中选中驱动器作为源模块时，"源接口"下拉框返回空），否则无法落地治理原则"驱动器经 CAN2/CANopen 连接主控"（见《总体设计》§2.1 原则5）。
【验收标准】选中任一 `subDriver` 组件作为连线源时，"源接口"下拉框必须包含至少 1 个 `CAN` 类型接口。
追溯：`audits/20260913_...` 问题2，**优先级 P0（阻断整车电气拓扑落地）**。

### 4.3 空间标定与接线 (MOUNTING / WIRING)

**REQ-MT-01** 传感器/执行器安装位姿（6-DOF）必须支持位置意图（"中心/顶部/…"）与坐标解算结果分离展示；当位置意图解算出全零坐标时，系统必须仍能将该组件标记为"已定位"（而非要求用户凑非零值来"骗过"状态机）。
追溯：`audits/20260913_...` 易用性问题4，**优先级 P1（用户可感知的错误状态语义）**。

**REQ-WR-01** 总线拓扑必须显式区分"主控 Host 总线端口"与"从设备总线端口"，即主控的 CAN_1/CAN_2/CAN_3 三条总线在 UI 上必须可视化区分，并强制约束从设备只能挂载到主控端口下（Bus Master-Slave），不得出现"平等展示所有 CAN 端点"的拓扑歧义。
【验收标准】接线视图中，主控 CAN 端口与从设备 CAN 端口使用不同视觉样式，且系统阻止"从设备→从设备"直连。
追溯：`design/implementation_plan.md` ISS-008；`specifications/ENGINEERING_CONSTRAINTS.md §11`。**优先级 P1**。

**REQ-WR-02** 主控 CAN2 上的驱动器连接必须显式标注协议为 CANopen；主控 CAN3 与 IO 扩展模块之间的连接必须显式标注协议为 UCAN。这两条治理规则当前在软件里**没有任何一处代码校验**，属于纯人工口头约定。
【验收标准】新增 P1 级审计规则：当驱动器被连接到非 CAN2 端口，或 IO 模块被连接到非 CAN3 端口时，审计页面给出 WARNING 或 ERROR。
追溯：用户提供的原始 5 条治理原则中的第 4/5 条；当前无任何自动化校验，属于**本次需求分析新发现的空白**（原实操报告未覆盖，因为报告聚焦于"能否连上"，未深入到"连到哪个编号端口"这一层）。**优先级 P1**。

**REQ-WR-03** RS485 总线上的多个从设备（电池、显示屏）必须能配置互不冲突的 `stationId`（站号）；当前私有属性模板未定义该字段。
【验收标准】RS485 总线下挂 ≥2 个从设备时，二者 `stationId` 不相等即可通过审计。
追溯：`audits/20260913_...` 问题6，审计严重度建议从纯信息提示上调，见 REQ-AU-02。**优先级 P1**。

**REQ-WR-04** IO 端口连接必须遵循"输出接输入"的反接线约束（主板 DI 只能接从设备 DO，主板 DO 只能接从设备 DI），并在 UI 连线校验中强制拦截违规连接。
追溯：`specifications/ENGINEERING_CONSTRAINTS.md §11`；当前实现程度未在本次实操中触达（因驱动器 CAN 接口缺失导致更上游的连线已受阻），需要在后端设计中明确校验点位置。**优先级 P1**。

### 4.4 能力映射与审计 (ABILITY / AUDIT)

**REQ-AB-01** 急停功能必须支持关联"防撞条"能力位（当前因目录无防撞条产品而无法绑定，属 REQ-CL-04 的下游阻塞项）。

**REQ-AU-01** 审计分级（ERROR 阻断导出 / WARNING 不阻断）的既有设计原则应保留，因其符合"先出模型、现场再校准接线"的工程习惯（`audits/20260913_...` 必要性 §1 的结论予以采纳）。**新增要求**：分级依据必须文档化为一张可维护的规则表（字段 → 严重度 → 理由），而不是分散在代码各处的隐式判断，便于后续新增规则时保持一致性。

**REQ-AU-02** RS485 `stationId` 缺失、CAN2/CAN3 协议错配（REQ-WR-02）应至少定为 WARNING 级（不建议与"组件能力未加载"这类纯信息提示同级），因为它们会导致真实下位机通信故障，风险高于普通占位性 WARNING。
追溯：`audits/20260913_...` 必要性 §4。

**REQ-AU-03** 审计错误必须精确定位到具体组件 UUID + 字段路径（`node_path`），不得只给出模块级别的笼统提示。
追溯：`requirements/RE-UNDERSTANDING.md §5`"加强审计反馈"既有目标，本次实操未发现回归，予以确认保留。

### 4.5 编译导出 (COMPILE / EXPORT)

**REQ-EX-01** "完成并云端编译"按钮点击后的失败必须返回结构化 JSON 错误（`{error, detail, node_path}`），不得将后端未捕获异常的原始堆栈/技术文案直接展示给终端用户。
【验收标准】人为制造一个校验失败场景（如字段超界），前端弹出的提示文案必须是业务语言（如"轮间距超出上限"），而不是"A Worker script … threw an unhandled exception"这类原始异常。
追溯：`audits/20260913_...` 问题7，**优先级 P0（当前已知会 100% 复现，导致普通用户完全无法通过正常路径导出）**。已确认根因为前端按钮请求构造/触发逻辑缺陷（同一 `/compile` 接口直接调用返回 200），非后端编译能力本身故障。

**REQ-EX-02** 预编译阶段的组件同步（PATCH 批量请求）中，任一组件同步失败时不得静默继续；必须汇总失败列表并阻止用户进入编译步骤，或至少在编译失败提示中列出哪些组件未同步成功。
追溯：`audits/20260913_...` 问题7 附带现象（`PATCH .../components/9923bc16-...→500`）。

**REQ-EX-03** "导出配置"按钮的实际行为（同步保存）与其命名（导出/下载）不一致，必须重命名或改为真实触发文件下载。
追溯：`audits/20260913_...` 问题8，**优先级 P2**。

## 5. 非功能性需求

**REQ-NF-01 数据保真（Bit-Perfect）**：Import→Export 往返必须保持 IEEE754 浮点精度与 Protobuf 标签顺序 100% 还原，`0`/`false`/`""` 等"假值"字段禁止在往返中被过滤丢弃。
追溯：`specifications/ENGINEERING_CONSTRAINTS.md §2`、`requirements/RE-UNDERSTANDING.md §3`。

**REQ-NF-02 Schema 驱动 / 禁止硬编码**：任何新增字段、类型判断、默认值必须来自 Schema（XML/JSON 模板），代码中不得出现字符串/数字字面量业务判断。
追溯：`CLAUDE.md`/`CONSTRAINTS.md` §1；`docs/ARCHITECTURE_DESIGN_AND_TECH_DEBT.md §3` 中列出的尚未清零的硬编码技术债（P0/P1/P2 共 10+ 项）应作为本次及后续迭代的强制清偿对象，不得新增同类债务。

**REQ-NF-03 原子化更新**：单组件修改必须对应后端单一 UUID 的原子 PATCH，避免高并发下的脏写。
追溯：既有 PRD §2.1，本次未发现回归。

**REQ-NF-04 可用性 — 无障碍操作**：所有可交互控件（含虚拟滚动列表、下拉框）必须在**不打开浏览器开发者工具**的前提下可通过标准鼠标/键盘操作完成选中，不允许出现依赖 `scrollIntoView()`+`click()` 才能命中的组件。
追溯：`audits/20260913_...` 易用性问题1，**优先级 P0（39 组件规模下普通用户几乎必然遇到无法选中的组件）**。

**REQ-NF-05 表单输入健壮性**：文本输入框的 Backspace/Delete 键必须与其余按键行为一致，不得出现新旧文本拼接乱码（如"StepStepko"）。
追溯：`audits/20260913_...` 易用性问题2，**优先级 P0（静默产生错误数据且无提示）**。
