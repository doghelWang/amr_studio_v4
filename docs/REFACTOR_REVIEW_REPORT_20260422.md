# AMR Studio V4 重构计划评审报告

日期：2026-04-22
评审方式：三视角联合评审
评审对象：AMR Studio V4 整体重构计划
结论等级：有条件通过

## 1. 评审背景

本次评审针对现有整体重构计划进行二次审视，目标不是重复给出“大而全”的愿景，而是回答以下问题：

- 当前计划是否抓住了项目的真实根因。
- 三人团队是否能在有限周期内执行。
- 哪些地方必须先做，哪些地方应延后。
- 下一步工作应该落在哪些具体产物上。

评审采用三种视角：

- 评审A：架构与边界视角
- 评审B：工程交付与团队协作视角
- 评审C：协议与领域一致性视角

## 2. 项目现状摘要

基于仓库现状，评审组确认以下事实：

- 项目核心价值不是“普通前后端管理系统”，而是“工业机器人配置编辑器 + 协议产物构建器”。
- 当前最重要的业务闭环是：导入 `.cmodel` -> 前端编辑 -> 后端沙箱同步 -> 导出 `.cmodel/.csv` -> 回归审计。
- 真正的复杂度不在 UI 页面数量，而在领域模型、协议模型、模块库模板、兼容规则、默认值策略和审计回归之间的耦合。
- 仓库中混合了主程序代码、运行产物、历史实验脚本、审计材料和测试样本，认知成本偏高。

## 3. 三方评审意见

### 3.1 评审A：架构与边界

结论：
原始重构计划方向正确，已经识别出“领域模型、协议映射、UI 状态、后端编排耦合过深”这个根因，但计划仍然偏大，边界设计需要进一步裁剪。

认可点：

- 先冻结契约和测试基线，再做结构重构，这个顺序是正确的。
- 将前端拆为 `app shell / features / domain / adapters / stores`，将后端拆为 `api / application / domain / infrastructure`，方向合理。
- 把导入导出管线独立出来，而不是继续埋在 store 和 route handler 里，是必须动作。

问题点：

- 计划对“事实源”治理提出了要求，但还没有明确什么是一级事实源，什么是兼容层。
- 当前代码存在两类默认值：Schema 默认值和 UX 默认值。原计划提到了这个冲突，但没有把它提升为正式设计决策。
- 后端的 `resource_adapter.py` 与 `data_manager.py` 已经事实上承担了多种职责。如果不优先拆这两处，后续边界仍会重新污染。
- 文档里存在部分规则互相冲突或阶段性遗留，比如子系统映射、扁平树与嵌套语义、模板填充与前端优先策略，需要在契约冻结阶段做决策表。
- 更关键的是，当前系统存在多套并行翻译层：前端 `ImportService` 做导入与拓扑推理，前端 `ExportService` 维护一套导出映射，后端 `resource_adapter` 维护另一套前后端转换，后端 `encoder` 在最终编译前再做清洗、改名、扁平化和容错。这说明根因不是“某个解析器太大”，而是“没有唯一 canonical model，也没有唯一转换责任边界”。
- 当前 `blueprint/modules` 更像可变中间格式，而不是稳定领域边界。它同时承担持久化、PATCH 落点和编译输入，而真正编译前还要做二次修正。如果不先降级它的契约地位，后续重构容易把补丁层正式固化。
- `Schema-First` 的所有权也没有真正成立。前端、后端、历史 `masterRegistry` 和 `/api/v1/schemas` 返回结构之间并未形成单一事实源，这比目录组织问题更根本。

架构风险判断：

- 最大风险不是“文件太大”，而是“未先冻结协议和默认值语义就开始搬代码”，这会直接造成隐蔽回归。
- 另一个一级风险是“把错误的中间表示固化为核心契约”。如果继续围绕当前 blueprint 与兼容层直接服务化，只会增加长期收敛成本。

P0 建议：

- 先做“契约冻结”，不要先做 monorepo 或大目录迁移。
- 先确定 4 套模型边界：UI Config、Canonical Domain Model、Protocol JSON、Proto Binary。
- 先拆后端 `main.py -> 用例服务` 和前端 `App/useProjectStore -> 领域纯函数`，其他拆分延后。
- 增加“单一事实源”决策：Proto、RobotConfig、blueprint、module JSON、XML/JSON schema、board interface 到底谁是源，谁是派生。
- 增加一条严格校验闸门：至少有一条运行时或 CI 黄金路径使用严格 proto 校验，而不是仅依赖兼容式清洗和忽略未知字段。

P1 建议：

- 生成式映射和 schema-runtime 放在第二阶段，不要与第一周交付耦合。
- 暂不追求一次性统一所有历史脚本目录，先标明“主路径”和“冻结区”。
- 前端 `ImportService` 中的拓扑推理、角色推断和能力 hydration 要被视为领域逻辑，而不是导入细节；后续应独立成 domain service。

### 3.2 评审B：工程交付与团队协作

结论：
原计划适合作为中长期蓝图，但对三人团队来说过宽。若不压缩范围，第一周大概率只会停留在“继续分析”，很难形成可验证成果。

认可点：

- 阶段化拆解是对的。
- 明确“先护栏、后结构、再体验”的顺序适合多人协作。
- 重视 golden tests 和回归基线，符合该项目风险特征。

问题点：

- 阶段太多，且每阶段都带有较重文档与结构改造任务，三人并行时容易出现依赖阻塞。
- 原计划缺少“第一周必须交付什么”的落地定义。
- 缺少人力分工与交付接口，如果三个人同时动同一层，会放大冲突。
- 当前仓库没有稳定的“主战区”定义，边做边清目录容易互相影响。

交付风险判断：

- 最大风险是“计划过载，里程碑过大”，导致三个人都在做基础设施，却没有拿到任何可验证的业务收益。

P0 建议：

- 第一周只做三件事：基线冻结、契约清单、最小拆分试点。
- 明确角色分工，尽量做到写集不重叠。
- 每周必须有一条可运行的回归链路作为演示结果。

P1 建议：

- 将“目录大迁移”“多包化”“生成式配置体系”放到第二周之后，以免吞掉节奏。
- 文档必须服务于执行，避免一次性补齐所有历史文档。

建议的三人职责：

- 成员1：协议与测试基线 owner
- 成员2：后端应用层重构 owner
- 成员3：前端领域拆分 owner

### 3.3 评审C：协议与领域一致性

结论：
重构计划最大的价值，在于它意识到本项目真正的“系统核心”是协议一致性，而不是页面组织；但原计划还需要把协议风险显式提升到第一优先级。

认可点：

- 已识别 `ImportService / ExportService / resource_adapter / encoder` 是核心高风险链路。
- 已识别当前 tests 里有较强的协议回归意图，如后端导出回归、API E2E、roundtrip 验证。

问题点：

- 部分测试仍然与环境路径、历史样本强耦合，还不能完全充当“重构护栏”。
- 现有文档中对 `No Hardcode` 的要求较强，但现实里存在大量必要兼容映射；需要区分“禁止新增硬编码”和“历史兼容层暂保留”。
- 对 `Schema default` 与 `UX default` 的冲突，目前代码和文档都承认存在，但没有形成统一判定规则。
- `resource_adapter.py` 中的类别映射、子系统映射和模板补全，是当前最容易发生语义偏移的地带。

协议风险判断：

- 最大风险是“在没有 golden fixture 与差异审计的情况下，逐步调整映射逻辑”，这样会出现导出成功但协议语义漂移。

P0 建议：

- 第一周必须建立可重复执行的黄金样本回归机制。
- 契约文档中必须新增“默认值策略表”和“兼容策略表”。
- 所有重构提交必须以 roundtrip 与导出回归通过为前置条件。

P1 建议：

- 后续再收敛系统审计脚本和历史 `audits/` 目录，不要与第一周重构主线混做。

## 4. 评审结论

综合结论：原重构计划方向正确，但范围过大。对于三人团队，必须裁剪为“两层计划”：

- 上层：保持原方案作为 4 到 6 周蓝图。
- 下层：立即执行 1 周内可交付的最小重构包。

结论判定：

- 原方案：有条件通过
- 执行前提：必须先补齐契约冻结、回归基线和第一周职责分工

## 5. 评审后的计划调整

### 5.1 保留项

- 先冻结契约与测试基线
- 后端分层重构
- 前端领域层拆分
- Schema/约束治理
- 工程化与 CI 完善

### 5.2 延后项

- 立即 monorepo 化
- 一次性目录大迁移
- 一次性统一全部历史脚本、审计目录和技能目录
- 过早引入生成式配置全链路改造

### 5.3 新增强制项

- 默认值策略决策表
- 兼容策略决策表
- 单一事实源说明
- 黄金样本回归清单
- 三人团队职责边界与写集约束

## 6. 下一步工作建议

评审组建议，下一步不直接做大规模代码迁移，而是先交付一个“第一周执行包”，其目标是：

- 让团队对系统边界形成统一语言
- 让重构具备自动化护栏
- 让三人可以并行开工且尽量少冲突

第一周执行包应包含：

- 一份裁剪后的 Sprint 1 计划
- 一份重构基线清单
- 一份契约冻结清单
- 一组黄金样本测试清单

## 7. 最终建议

可以继续推进整体重构，但执行口径必须从“全面改造”切换为“护栏先行、逐层替换、每周可验收”。三人团队当前最优策略不是全面铺开，而是：

- 先固定协议和测试护栏
- 再拆后端应用层
- 同时小步拆前端领域层
- 最后再治理 schema-runtime 与目录结构

这会比直接大迁移更慢一点开始，但会显著降低返工概率。
