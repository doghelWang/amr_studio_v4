# mac 平台模拟验证方案

## 1. 目的

当前项目文档已经明确真实落地方向是 `RK3588 + Linux + Python 插件外壳 + Worker 子进程 + 编译算法核心`。  
在进入正式研发前，先在 mac 平台完成架构级验证，目标不是验证识别精度，而是验证以下高风险设计假设：

- 主进程只看到一个轻量 Python 入口时，调用链是否足够稳定
- 高风险逻辑移入 Worker 子进程后，心跳、结果、失败、超时是否可控
- 5 秒确定性返回机制是否成立
- 主进程与插件之间的接口契约是否足够清晰，便于后续替换为真实算法核心

## 2. 从现有文档提炼出的关键约束

- 对外必须保持 Python 插件调用形态
- 不应把重计算和高风险依赖直接放进主进程同一解释器
- 识别过程允许多帧，但必须在 `5s` 内得到明确结果
- 处理中需要对外可见的状态反馈
- 返回结果应标准化，推荐 JSON
- 后续真实环境需要支持授权、资源限制、网络采集和算法核心替换

## 3. 本轮验证范围

本轮只验证“架构最小闭环”，不验证真实识别算法与硬件接入：

- 主进程模拟器调用 `plugin_api.py`
- `plugin_api.py` 拉起独立 `worker.py`
- Worker 周期性发送 heartbeat
- Worker 返回成功 / 失败 / 超时三类结果
- `plugin_api.py` 实施 5 秒硬超时
- `plugin_api.py` 模拟调用主进程 Python 回调

## 4. 目录与职责

新增目录：`mac_mock/`

- `simulate_host.py`
  - 模拟未知主进程
  - 只通过命令行调用插件入口
- `plugin_api.py`
  - 模拟正式交付中的 Python 外壳
  - 管理 Worker 生命周期
  - 转发 heartbeat
  - 做超时熔断
  - 输出标准结果
- `worker.py`
  - 模拟独立识别进程
  - 模拟多帧处理和状态上报
  - 模拟成功 / 失败 / 超时路径
- `config.json`
  - 承载运行时参数与任务参数

## 5. 当前验证结论

这套 mock 可以先验证四个最关键问题：

1. 主进程是否只依赖稳定的 Python 入口，而不接触算法实现细节。
2. Worker 是否能作为独立故障边界存在。
3. 心跳与最终结果是否能被统一建模。
4. 5 秒硬超时是否能在插件外壳层被强制执行。

如果这四点在 mac 平台模拟通过，就可以继续把真实内容按层替换进去：

- 把 `worker.py` 中的模拟逻辑替换成真实网络采集
- 把模拟结果生成替换成图像/点云算法
- 把授权占位替换成真实 license 校验
- 把 JSON stdout 协议替换成更正式的 IPC 协议

## 6. 建议下一步

建议按以下顺序推进：

1. 固化主进程与插件之间的输入/输出 JSON 契约。
2. 在 mock 上补充错误码、阶段耗时和结构化日志字段。
3. 将 Worker 的 stdout 协议抽象为事件协议，避免后续真实接入时重写主流程。
4. 在第二轮验证中引入假数据源，模拟 TCP/UDP 图像帧和点云帧输入。
5. 在第三轮验证中再替换为真实算法核心或 `.so` 占位模块。
