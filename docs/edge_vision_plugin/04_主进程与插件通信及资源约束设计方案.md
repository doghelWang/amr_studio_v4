# 主进程与插件通信及资源约束设计方案

## 1. 目标

在保持“主进程只调用 Python 插件入口”的前提下，定义一套后续可直接替换真实算法核心的正式机制，包括：

- 主进程与插件的接口边界
- 插件壳与 Worker 的 IPC 协议
- 事件模型与结果模型
- CPU / 内存 / 线程等资源约束的接口获取与下发机制

## 2. 分层机制

```mermaid
flowchart LR
    A["主进程"] --> B["plugin_api.py<br/>Python 插件壳"]
    B --> C["Worker 子进程"]
    C --> D["算法核心 / 网络采集 / 授权核心"]
```

- 主进程只依赖 `plugin_api.py` 暴露的稳定调用接口
- `plugin_api.py` 负责参数校验、超时熔断、回调适配、资源约束注入
- Worker 负责真实执行与状态上报
- 算法核心可以替换成 Python mock、`.so`、独立服务适配层

## 3. 通信机制

### 3.1 主进程 -> 插件壳

推荐保持同步函数调用或命令式调用，输入一个 `TaskRequest`，输出一个 `TaskResult`。

最小输入结构：

```json
{
  "task_id": "task_001",
  "object_id": "target_a",
  "object_type": "box",
  "config_path": "./config.json",
  "timeout_ms": 5000
}
```

最小输出结构：

```json
{
  "status": "success",
  "task_id": "task_001",
  "object_id": "target_a",
  "x": 123.4,
  "y": 52.1,
  "z": 18.7,
  "yaw": 91.2,
  "confidence": 0.93,
  "elapsed_ms": 3010,
  "message": "ok"
}
```

### 3.2 插件壳 -> Worker

推荐正式采用 `stdin request + stdout NDJSON event stream`。

原因：

- 与语言无关，后续 Worker 不一定必须是 Python
- 避免命令行参数膨胀
- 便于扩展握手、资源协商、阶段状态、诊断信息
- 更接近后续真实部署中的标准 IPC 形态

## 4. IPC 契约

### 4.1 请求消息

插件壳向 Worker 发送单条请求 JSON：

```json
{
  "protocol_version": "1.0",
  "request_id": "uuid",
  "task": {},
  "runtime": {},
  "resource_contract": {},
  "scenario": {}
}
```

字段说明：

- `protocol_version`: 协议版本，便于向后兼容
- `request_id`: 整个任务链路的唯一 ID
- `task`: 业务任务参数
- `runtime`: 超时、轮询、心跳等运行参数
- `resource_contract`: 主进程或插件侧下发的资源约束
- `scenario`: mock 或真实执行策略

### 4.2 事件消息

Worker 通过 stdout 持续输出事件流，每条为一行 JSON：

```json
{
  "protocol_version": "1.0",
  "event_id": "uuid",
  "event_type": "task.progress",
  "source": "worker",
  "request_id": "uuid",
  "task_id": "task_001",
  "timestamp_ms": 1710000000000,
  "payload": {}
}
```

### 4.3 建议事件类型

- `worker.ready`
- `task.accepted`
- `task.progress`
- `task.result`
- `task.error`
- `task.resource_snapshot`
- `task.log`

## 5. 接口约束

### 5.1 主进程接口约束

- 主进程不得直接加载 Worker 或算法核心
- 主进程只和 `plugin_api.py` 的稳定入参/出参交互
- 主进程不依赖 heartbeat 内部字段，只依赖状态语义
- 主进程必须接受三类终态：`success`、`failed`、`timeout`

### 5.2 插件壳接口约束

- 必须做请求校验、超时熔断、异常兜底
- 必须将 Worker 的异常转换成标准结果
- 不允许在壳层承载重计算或点云/视觉核心
- 必须向主进程返回统一结构的结果对象

### 5.3 Worker 接口约束

- 启动后必须先输出 `worker.ready`
- 接到请求后必须输出 `task.accepted`
- 长任务必须周期性输出 `task.progress`
- 必须输出单一终态：`task.result` 或 `task.error`
- 不得把非结构化日志混写到 stdout 事件流

## 6. 资源约束接口设计

### 6.1 资源契约输入

由配置或主进程注入到插件壳，再由插件壳原样下发给 Worker：

```json
{
  "cpu": {
    "max_cores": 1,
    "affinity_enabled": false,
    "affinity_cores": [],
    "nice": 10,
    "thread_limits": {
      "omp": 1,
      "openblas": 1,
      "mkl": 1,
      "opencv": 1
    }
  },
  "memory": {
    "limit_mb": 1024,
    "high_watermark_mb": 900
  },
  "io": {
    "max_inflight_frames": 5,
    "max_frame_bytes": 8388608
  }
}
```

### 6.2 资源约束接口获取设计

资源约束来源建议分三层，按优先级覆盖：

1. 主进程显式下发
2. 插件配置文件默认值
3. 平台探测默认值

建议插件壳暴露一个统一方法：

```python
def resolve_resource_contract(
    host_limits: dict | None,
    config_limits: dict,
    platform_defaults: dict,
) -> dict:
    ...
```

### 6.3 CPU 约束接口

插件壳或 Worker 在启动前执行：

- 读取 `cpu.max_cores`
- 读取 `cpu.affinity_enabled`
- 读取 `cpu.affinity_cores`
- 读取 `cpu.nice`
- 读取 `cpu.thread_limits.*`

对应实现挂点：

- `os.nice()`
- `os.sched_setaffinity()` 或平台替代逻辑
- 环境变量注入：
  - `OMP_NUM_THREADS`
  - `OPENBLAS_NUM_THREADS`
  - `MKL_NUM_THREADS`
- OpenCV 线程数设置入口

### 6.4 内存约束接口

Worker 启动后优先应用：

- `memory.limit_mb`
- `memory.high_watermark_mb`

对应实现挂点：

- `resource.setrlimit(resource.RLIMIT_AS, ...)`
- 周期性内存采样
- 触达高水位后的降级策略

### 6.5 资源状态回传

建议 Worker 定期或在关键阶段输出 `task.resource_snapshot`：

```json
{
  "rss_mb": 312,
  "cpu_percent": 86.5,
  "thread_count": 3,
  "inflight_frames": 2
}
```

## 7. 推荐演进路径

1. 当前 mock 阶段先固定 `stdin/stdout` 协议和事件类型。
2. 第二阶段把资源契约真实注入 Worker 启动环境。
3. 第三阶段接入假 TCP/UDP 数据源与授权模块占位。
4. 第四阶段将 Worker 内 mock 逻辑替换为真实算法核心或 `.so` 调用。

## 8. 结论

最稳妥的机制是：

- 主进程只依赖 Python 插件壳
- 插件壳与 Worker 通过正式的 `stdin request + stdout event stream` 通信
- 所有资源约束由统一 `resource_contract` 描述并下发
- 所有终态结果和过程状态都走结构化事件

这样后续即使替换真实算法核心、授权模块或网络采集模块，也不需要重做主进程与插件之间的协作边界。
