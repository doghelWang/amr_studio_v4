## 2. 项目背景

AMR Studio V4 的核心目标是提供一个面向 AMR 机器人模型配置、解析、编辑、校验和导出的工程工具。系统需要读取 `.cmodel` 模型文件，解析其中的组件描述、能力集合和功能描述，允许用户在前端完成装配、参数、安装位置、电气连接、能力映射和功能过程配置，并最终导出客户端可识别的 `.cmodel` 成果物。

经过前期重构，后端已完成较大规模模块化拆分，具备 `.cmodel` 上传解析、项目沙箱、组件拆分、能力/功能读取、编译导出、debug artifacts 等基础能力。前端已初步补齐电气连接和功能能力的 P0/P1 能力，但仍需要以完整产品需求的方式固化边界、验收标准和后续任务。

## 3. 核心问题

### 3.1 解析与生成链路问题

- `.cmodel` 文件由 `CompDesc`、`AbiSet`、`FuncDesc` 等多个协议文件组成，不能只处理组件描述。
- 历史实现中存在部分字段默认值、模块描述、类型、子系统等信息由代码推断或硬编码生成的风险。
- protobuf 字段命名、CamelCase/SnakeCase、COMBOX 嵌套结构、FIXED_E 引用等规则复杂，存在静默丢字段风险。
- 部分异常模型本身不完整或损坏，不能把所有解析失败都归因于解析器缺陷。

### 3.2 前端模型表达问题

- 当前 UI 历史上更偏组件表单配置，电气连接、能力和功能过程不是完整的一等领域模型。
- `linkedInterfaceUuid` 是真实模型中的关键连接字段，但此前 UI 难以完整展示连接来源、方向、类型、诊断和拓扑。
- `AbiSet.componentAbility` 不能继续被忽略。
- `FuncDesc.function` 必须至少可见、可审计，后续再逐步支持结构化编辑。

### 3.3 模块库事实源问题

- 模块库事实源包含 `specifications/ModuleLibrary/Aggregated/*.xml`、离散 JSON、运行时模块模板等多类数据。
- 后续不能继续依赖模块名、字段名、描述文本进行业务推断。
- 需要建立统一模块库注册表，提供主类型、子类型、接口类型、私有属性、能力约束、板卡接口等事实查询。

### 3.4 测试与验证问题

- 单一参考模型覆盖不足。
- `ModelSet.cmodel`、`20260612.cmodel`、`校验模型.cmodel` 分别覆盖差速、舵轮、升降/旋转、BAT、screen、多 IO、多传感器等不同场景。
- `proj*` 打头的模型很多来自历史导出、调试产物或异常构建产物，不能默认作为标准参考模型。
- 需要同时保留标准 golden fixture 和异常兼容性样本。

## 4. 总体目标

### 4.1 产品目标

AMR Studio V4 应成为一个可审计、可追溯、可回归验证的 AMR 模型配置工具，能够支持真实业务 `.cmodel` 的导入、展示、编辑、校验和导出。

### 4.2 技术目标

- 后端完成模块化、可测试、可诊断的解析生成链路。
- 前端完成组件、接口、电气连接、能力、功能过程的一等领域建模。
- 模块库从散落模板和硬编码映射升级为统一注册表。
- 所有导入/编辑/导出过程具备 debug artifacts 和验证报告。
- 禁止通过猜测、创造、假想补齐协议字段、参数、描述、类型、连接或能力内容。

## 5. 强制约束

### 5.1 禁止猜测与创造

系统严禁通过猜测、臆断、创造、假想的方式补齐任何参数值、描述信息、模块内容、能力内容、连接关系或协议字段。

当事实源不存在时，只允许：

- 保持缺失。
- 标记为未知。
- 输出结构化诊断。
- 阻断导出。
- 使用已登记在正式规范中的兜底值。
- 等待用户显式输入。

### 5.2 字段来源可追溯

所有进入导出成果物的字段必须能追溯到以下来源之一：

- 导入 `.cmodel` 中的 `CompDesc`、`AbiSet`、`FuncDesc`。
- protobuf schema。
- 模块库模板或聚合 XML。
- 后端注册表。
- 用户显式输入。
- 正式工程约束中登记的兜底规则。

### 5.3 异常模型分类

模型样本必须分类管理：

- 标准参考模型：用于业务正确性和 roundtrip 断言。
- 覆盖扩展模型：用于增强类型、接口、能力覆盖。
- 异常/历史模型：用于错误处理、诊断能力和兼容性测试。
- 空白/非完整模型：不得作为业务完整性参考。

`proj*` 打头模型默认不作为标准参考模型，除非人工确认其来源和完整性。

### 5.4 数据无损

- 不得过滤 `0`、`false`、`""` 等合法值。
- 不得丢弃 `componentAbility`、`version`、空值状态等非 UI 直接编辑字段。
- 导入模型中的 UUID、接口 UUID、连接引用、能力和功能过程应尽可能原样保留。

### 5.5 扁平模块树要求

客户端当前基线要求模块在根级 `moreModuleInfo` 下平铺。后端导出应保持扁平结构，并通过 `parentNodeUuid` 表达父子关系。

### 5.6 连接完整性要求

导出前必须校验所有 `linkedInterfaceUuid` 都能在当前模型内找到对应 `interfaceUuid`。若存在悬挂连接，必须阻断导出或输出明确错误诊断。

## 6. 用户角色

### 6.1 模型配置工程师

负责导入已有 AMR 模型、检查组件与参数、调整安装坐标、维护电气连接、导出模型成果物。

### 6.2 电气/硬件工程师

关注接口类型、接线关系、IO 方向、总线拓扑、电源/BAT/SPI/ETH/CAN 等连接完整性。

### 6.3 软件/功能工程师

关注能力映射、功能过程、组件能力与 `FuncDesc` 是否匹配。

### 6.4 平台维护者

关注模块库注册表、协议兼容、异常模型诊断、部署、回归测试和版本管理。

## 7. 范围定义

### 7.1 本阶段范围

- `.cmodel` 上传、解析、项目沙箱落盘。
- `CompDesc` 组件、接口、安装坐标、连接关系解析。
- `AbiSet` 能力解析和保留。
- `FuncDesc` 功能过程解析和只读摘要。
- 前端组件装配、安装坐标、电气连接清单、基础连接创建/删除。
- 审计页汇总组件、接口、连接、能力、功能过程诊断。
- 后端编译导出 `.cmodel`。
- debug artifacts 留存。
- 批量模型分析和 golden fixture 建设。

### 7.2 暂不作为本阶段强制范围

- 完整图形化拓扑画布。
- 完整 `FuncDesc` 可视化流程编辑器。
- 所有模块私有属性的高级业务约束编辑。
- 多人协同编辑。
- 权限系统。
- 正式生产级前端静态服务替换方案之外的云平台治理。

## 8. 功能需求

### 8.1 CModel 模型文件解析

#### FR-CMODEL-PARSE-001 模型包识别

系统应支持识别 `.cmodel` 模型文件的包结构，并定位其中的模型描述文件。

至少应识别：

- `ModelFileDesc`
- `CompDesc.model`
- `AbiSet.model`
- `FuncDesc.model`

验收标准：

- 能判断模型包是否包含完整的组件描述、能力描述和功能描述。
- 对缺失文件输出结构化诊断，不得静默忽略。
- 对空白模型、异常模型、历史导出模型进行错误分类。

#### FR-CMODEL-PARSE-002 protobuf 反解析

系统应基于项目内 proto 定义，将 `.model` 二进制文件反解析为 JSON。

验收标准：

- `CompDesc.model` 可反解析为 `CompDesc.json`。
- `AbiSet.model` 可反解析为 `AbiSet.json`。
- `FuncDesc.model` 可反解析为 `FuncDesc.json`。
- 解析失败时返回目标 message 类型、失败阶段和原始异常摘要。
- 不允许在解析失败时生成伪 JSON 或空白替代结构冒充真实解析结果。

#### FR-CMODEL-PARSE-003 解析产物保留

系统应保留解析过程中的关键产物，支持脱离前端界面调试。

至少应保留：

- 原始上传 `.cmodel`。
- 解包后的原始文件列表。
- 反解析后的 `CompDesc.json`、`AbiSet.json`、`FuncDesc.json`。
- 模块拆分后的 `blueprint_CompDesc.json` 和 `modules/*.json`。
- 解析失败时已产生的中间文件和诊断报告。

#### FR-CMODEL-PARSE-004 解析结果摘要

系统应在解析完成后生成摘要信息。

摘要至少包含：

- 组件数量。
- 接口数量。
- 连接引用数量。
- 悬挂连接数量。
- `componentAbility` 数量。
- `functionAbility` 数量。
- `FuncDesc.function` 数量。
- 解析诊断列表。

### 8.2 CModel 解析结果结构化展示

#### FR-PARSE-VIEW-001 器件清单

系统应基于解析后的 `CompDesc` 生成器件清单。

字段至少包括：

- 模块 UUID。
- 模块名称。
- 模块描述。
- 主类型。
- 子类型。
- 所属分组。
- 接口数量。
- 私有属性摘要。
- 来源模型与解析状态。

约束：

- 器件名称、描述、类型必须来自模型文件或模块库事实源。
- 对缺失或未知类型应展示未知状态和诊断，不得根据文件名或模块名猜测。

#### FR-PARSE-VIEW-002 安装位置清单

系统应基于解析后的 `structParam.extendParams` 生成安装位置清单。

字段至少包括：

- 组件 UUID。
- 组件名称。
- `locCoordX`
- `locCoordY`
- `locCoordZ`
- `locCoordROLL`
- `locCoordPITCH`
- `locCoordYAW`
- `parentNodeUuid`

约束：

- 只展示模型中真实存在或用户明确配置的安装字段。
- 缺失安装字段应显示为缺失或待配置。
- 不得基于组件类型或名称推断安装方位。

#### FR-PARSE-VIEW-003 连接说明

系统应基于 `interfaceParams.interfaceGroup[].linkedInterfaceUuid` 生成连接说明。

连接说明至少包括：

- 源组件。
- 源接口。
- 源接口类型。
- 目标组件。
- 目标接口。
- 目标接口类型。
- 连接类别。
- 连接方向。
- 是否存在悬挂目标。
- 连接诊断。

验收标准：

- 能从已导入模型中完整列出连接关系。
- 对同一连接的双向引用或重复引用应能合并展示。
- 对无法反查目标接口的连接应明确标记为悬挂连接。

### 8.3 CModel 导入

#### FR-IMPORT-001 上传模型

系统应支持上传 `.cmodel` 文件到后端服务。

验收标准：

- 成功模型返回 `project_id`。
- 成功模型落盘到独立 `saved_projects/{projectId}`。
- 成功模型至少应生成或保留 `CompDesc.json`、`AbiSet.json`、`FuncDesc.json` 中可解析的文件。
- 失败模型不得只返回泛化 500，应返回结构化诊断。

#### FR-IMPORT-002 解码与拆分

系统应将 `.model` protobuf 文件解码为 JSON，并将组件拆分为项目内模块文件。

验收标准：

- 保留原始组件 UUID。
- 保留原始接口 UUID。
- 保留 `linkedInterfaceUuid`。
- 保留原始空值状态。
- 拆分结果可以重新聚合为可导出结构。

#### FR-IMPORT-003 异常模型诊断

对于缺失 `CompDesc`、protobuf 解析失败、包结构异常等情况，系统应输出明确诊断。

验收标准：

- 缺失 `CompDesc.json` 返回类似 `CMODEL_COMPDESC_MISSING`。
- protobuf 类型解析失败返回目标 message 类型和失败阶段。
- 后端保留失败解包的关键中间产物，便于脱离前端调试。

### 8.4 组件与模块管理

#### FR-COMP-001 组件清单

系统应展示模型中的全部组件。

字段至少包括：

- `moduleUuid`
- `moduleName`
- `moduleDesc`
- `mainModuleType`
- `subModuleType`
- `groupName`
- 接口数量
- 安装坐标摘要

#### FR-COMP-002 模块库装配

用户应能从模块库中添加组件。

约束：

- 组件字段必须来自模块库模板或用户输入。
- 不允许根据名称猜测组件类型。
- 若模板缺失，应输出诊断而不是生成伪模板。

#### FR-COMP-003 私有属性

系统应保留并展示私有属性分组。

约束：

- 私有属性必须位于 `privateAttr.privateAttrs`。
- 不得扁平化到 `structParam.extendParams`。
- `DATA_COMBOX` 当前值必须以 `comboType.typeKey` 为准。

### 8.5 模块库与属性管理

#### FR-LIB-001 模块分类管理

系统应管理模块库中的模块分类。

分类至少包括：

- 底盘。
- 驱动轮。
- 驱动器。
- 电机。
- 主控。
- 扩展接口模块。
- 传感器。
- 电池。
- 灯光。
- 按钮。
- 音频。
- 屏幕。
- 执行器。
- 复合模块。

约束：

- 分类必须来自模块库配置或注册表。
- 不得通过模块名称子串推断分类。
- 对模块库中存在但前端未识别的分类应输出诊断并保留原始分类。

#### FR-LIB-002 通用属性管理

系统应管理模块通用属性。

通用属性至少包括：

- `moduleName`
- `moduleDesc`
- `moduleUuid`
- `versionInfo`
- `subSysType`
- `mainModuleType`
- `subModuleType`
- `moduleDscType`
- `venderName`
- `moduleShape`

约束：

- 通用属性默认值必须来自模型、模块库模板或正式兜底规范。
- 空 `moduleDscType.typeKey`、空 `venderName.typeKey` 应保持空值并输出诊断，不得用描述或模块名补造。

#### FR-LIB-003 私有属性管理

系统应管理模块私有属性模板和实例值。

要求：

- 支持按属性组展示。
- 支持 `DATA_STRING`、`DATA_DOUBLE`、`DATA_UINT32`、`DATA_BOOL`、`DATA_COMBOX`、`DATA_FIXED_E` 等类型。
- 支持 `DATA_COMBOX` 选中分组解析。
- 支持 `DATA_FIXED_E` 根据 `fixedSource` 做候选过滤。

约束：

- 私有属性事实源必须来自模块库或导入模型。
- 不得在 React 组件中硬编码某类模块的私有属性表。

#### FR-LIB-004 复合模块管理

系统应支持复合模块的定义、展开和实例化。

复合模块至少应覆盖：

- 底盘与轮组组合。
- 舵轮与驱动器/电机组合。
- 差速舵轮与外置编码器组合。
- 主控与板载接口/扩展接口组合。

约束：

- 复合模块展开规则必须来自模块库配置或正式工程约束。
- 自动生成的子组件必须标记来源。
- 若缺少复合模块定义，不得根据名称猜测生成子模块。

### 8.6 安装位置与机械拓扑

#### FR-MOUNT-001 安装坐标

系统应解析和编辑 `locCoordX/Y/Z/ROLL/PITCH/YAW`。

约束：

- 只读取真实存在于 `structParam.extendParams` 的安装字段。
- 缺失字段显示为缺失或待配置。
- 不得用组件名或类型推断安装位置。

#### FR-MOUNT-002 父子关系

系统应支持通过 `parentNodeUuid` 表达机械父子关系。

验收标准：

- 导入时能读取原始 `parentNodeUuid`。
- 导出时能保持 `parentNodeUuid`。
- 扁平模块树下仍可通过该字段重建前端树视图。

### 8.7 模型文件构建流程

#### FR-BUILD-001 底盘选型

系统应支持以底盘选型作为模型构建入口。

底盘选型至少包括：

- 底盘类型。
- 底盘尺寸。
- 形状。
- 运动机构类型。
- 载荷/速度/加速度等底盘相关参数。

约束：

- 可选底盘类型和参数模板必须来自模块库。
- 用户未选择或未输入的字段不得被业务猜测填充。

#### FR-BUILD-002 器件选择和搭建

系统应支持用户从模块库选择器件并搭建模型。

能力至少包括：

- 添加器件。
- 删除器件。
- 配置器件通用属性。
- 配置器件私有属性。
- 配置安装位置。
- 配置父子关系。
- 通过复合模块规则生成必要子组件。

验收标准：

- 新增器件具备合法 UUID。
- 新增器件属性来源可追溯。
- 复合模块生成过程可审计。

#### FR-BUILD-003 连接关系配置

系统应支持用户在器件搭建后配置接口连接关系。

能力至少包括：

- 按器件筛选接口。
- 按接口类型筛选接口。
- 创建连接。
- 删除连接。
- 查看连接诊断。
- 查看总线连接组。

约束：

- 连接必须基于真实接口实例。
- 连接参数必须来自接口定义或用户输入。
- 不得根据器件类型自动创建业务连接，除非复合模块规则中明确登记。

#### FR-BUILD-004 软件功能配置选择

系统应支持用户选择和配置软件功能。

软件功能至少包括：

- 能力类型选择。
- `componentAbility` 查看和保留。
- `functionAbility` 配置。
- `FuncDesc` 功能过程查看。
- 功能与器件、接口、连接的关联诊断。

约束：

- 不得根据已选择硬件自动创造功能过程。
- 若模板中存在功能过程，可作为模板来源并标记来源。
- 若用户显式选择功能，应记录用户输入来源。

#### FR-BUILD-005 分步构建状态

系统应展示模型构建进度。

步骤至少包括：

- 底盘已选择。
- 器件已搭建。
- 安装位置已配置。
- 连接关系已配置。
- 软件功能已配置。
- 审计已通过。
- 可导出。

### 8.8 电气接口

#### FR-IFACE-001 接口实例

系统应从组件中解析接口实例。

字段至少包括：

- `interfaceUuid`
- `key`
- `type`
- `desc`
- `linkedInterfaceUuid`
- `interfaceAttrs`
- `interfaceParams`

#### FR-IFACE-002 接口类型

系统应支持至少以下接口类型：

- 通信：`CAN`、`ETH`、`RS485`、`RS232`、`UART`、`USB`、`SPI`、`LVDS`。
- IO：`DI`、`DO`、`AI`、`AO`、`PI`、`PO`。
- 电源/电池：`BAT`、`POWER`、`PWR`。
- 音视频/功能：`SPK`、`SMA`、`HDMI`、`ENCR`、`LINE`。

约束：

- 接口类型集合应来自模块库注册表。
- 未知接口类型应显示为 unknown 并输出诊断，不得强行归类。

### 8.9 电气连接

#### FR-WIRE-001 连接实体

前端应将 `linkedInterfaceUuid` 反建为一等 `ElectricalConnection` 实体。

实体字段至少包括：

- 连接 ID。
- 源组件与源接口。
- 目标组件与目标接口。
- 接口类型。
- 连接类别。
- 连接方向。
- 连接来源。
- 诊断信息。

#### FR-WIRE-002 连接展示

系统应在 UI 中展示连接清单。

验收标准：

- 能看到源组件、源接口、目标组件、目标接口。
- 能看到接口类型和连接类别。
- 能看到缺失目标、类型不兼容、重复引用等诊断。

#### FR-WIRE-003 连接创建与删除

用户应能创建和删除基础连接。

约束：

- 创建前必须校验源接口和目标接口存在。
- 创建前必须校验接口类型兼容。
- 点对点接口不得被重复占用。
- `CAN`、`RS485` 等总线接口可支持多点连接，但必须显式归类为总线连接。
- 删除连接必须清理相关 `linkedInterfaceUuid`。

#### FR-WIRE-004 IO 方向校验

IO 信号必须遵循输入连接输出原则。

规则：

- `DI` 应连接 `DO`。
- `DO` 应连接 `DI`。
- `AI` 应连接 `AO`。
- `AO` 应连接 `AI`。
- `PI` 应连接 `PO`。
- `PO` 应连接 `PI`。

#### FR-WIRE-005 连接完整性

导出前必须校验所有连接引用无悬挂。

验收标准：

- 标准 golden fixture 导入后连接悬挂数为 0。
- 导出前若存在悬挂连接，审计页必须显示错误。
- 编译接口应拒绝存在悬挂连接的项目，除非明确处于诊断导出模式。

### 8.10 总线类型、属性参数与状态管理

#### FR-BUS-001 总线类型管理

系统应管理总线类型及其接口定义。

本阶段至少覆盖：

- `CAN`
- `ETH`
- `RS485`

后续可扩展：

- `RS232`
- `UART`
- `USB`
- `SPI`

约束：

- 总线类型必须来自模块库接口定义或注册表。
- 未登记总线类型不得被强行归类。

#### FR-BUS-002 总线属性参数管理

系统应管理总线属性参数。

参数可包括但不限于：

- 总线名称。
- 总线类型。
- 主站接口。
- 从站接口列表。
- 波特率或速率。
- 协议参数。
- 端口号或通道号。
- 终端电阻/终端配置。
- IP、端口、网段等 ETH 参数。

约束：

- 参数字段必须来自接口定义、模块库、原模型或用户输入。
- 对未定义参数不得自动补造默认值。
- 不同总线类型应展示各自真实存在的参数集合。

#### FR-BUS-003 总线信息管理

系统应将多点总线连接组织为总线信息实体。

总线信息至少包括：

- 总线 ID。
- 总线类型。
- 主设备。
- 主接口。
- 从设备列表。
- 从接口列表。
- 关联连接列表。
- 参数摘要。
- 诊断信息。

验收标准：

- 能从 `linkedInterfaceUuid` 连接中识别 `CAN`、`ETH`、`RS485` 总线组。
- 能展示一个主接口挂载多个从接口的拓扑。
- 能发现同一从接口挂到多个互斥总线的错误。

#### FR-BUS-004 总线状态管理

系统应管理模型配置态的总线状态。

状态至少包括：

- `unconfigured`：总线接口存在但未连接。
- `configured`：总线连接完整。
- `warning`：连接存在非阻断诊断。
- `error`：存在悬挂连接、类型不兼容或参数缺失。
- `unknown`：缺少事实源，无法判断。

约束：

- 这里的状态是模型配置状态，不等同于设备运行时在线/离线状态。
- 若未来接入运行时状态，必须有明确的数据源，不得由模型配置推断运行时健康状态。

### 8.11 能力集合

#### FR-ABILITY-001 componentAbility

系统应完整读取、展示和保留 `AbiSet.componentAbility`。

验收标准：

- 导入后数量不丢失。
- 导出后数量不被清空。
- 未支持编辑的字段以只读方式展示。

#### FR-ABILITY-002 functionAbility

系统应读取、展示、编辑和导出 `AbiSet.functionAbility`。

约束：

- FIXED_E 关联必须基于真实组件或用户选择。
- 不得根据能力名称自动选择组件。
- 若关联目标不存在，应输出诊断。

#### FR-ABILITY-003 能力来源

能力数据应标记来源：

- 导入模型。
- 能力注册表。
- 用户编辑。
- 模块库或后端注册表。

### 8.12 功能过程 FuncDesc

#### FR-FUNC-001 功能过程读取

系统应从 `FuncDesc` 读取 `function[]` 和 `childFunction`。

验收标准：

- 导入后功能过程数量可见。
- 功能节点 `type`、`desc`、关键 attr 可查看。
- 原始 `FuncDesc` 可保留用于导出。

#### FR-FUNC-002 只读摘要

本阶段前端至少应提供只读功能过程摘要。

约束：

- 不自动创建功能过程。
- 不根据 `functionAbility` 反推 `FuncDesc.function`。
- 缺失 `FuncDesc` 时显示缺失诊断。

#### FR-FUNC-003 后续编辑能力

后续阶段应支持结构化编辑：

- 功能节点新增/删除。
- 功能节点关联能力。
- 功能节点关联组件。
- 功能节点关联连接。
- 功能过程完整性校验。

### 8.13 模型文件总结和导出

#### FR-AUDIT-001 审计页

审计页应汇总：

- 组件数。
- 接口数。
- 连接数。
- 能力数。
- 功能过程数。
- 错误、警告、信息级诊断。

#### FR-AUDIT-002 导出前校验

导出前必须执行：

- 组件 UUID 完整性校验。
- 接口 UUID 完整性校验。
- `linkedInterfaceUuid` 完整性校验。
- 主类型/子类型合法性校验。
- 接口类型合法性校验。
- `AbiSet` 保真校验。
- `FuncDesc` 保真校验。

#### FR-SUMMARY-001 模型总结

系统应在导出前生成模型总结。

总结至少包括：

- 整车基本信息。
- 底盘选型。
- 器件清单。
- 安装位置清单。
- 电气连接说明。
- 总线信息与状态。
- 能力配置。
- 功能过程摘要。
- 导出风险与诊断。

约束：

- 总结必须来自当前项目事实数据。
- 不得为了摘要完整性补造不存在的描述或参数。

#### FR-EXPORT-001 导出 CModel

系统应支持将当前项目编译为 `.cmodel`。

验收标准：

- 返回 `.cmodel` 下载地址。
- 返回模块清单 CSV 下载地址。
- 返回 audit 日志。
- 生成 debug artifacts。

#### FR-EXPORT-002 调试产物保留

导出和调试过程中应保留：

- 前端导出配置 JSON。
- 后端解析后中间 JSON。
- 生成前 `CompDesc`。
- 清洗后 `CompDesc`。
- 最终 `CompDesc.model`、`AbiSet.model`、`FuncDesc.model`。
- 最终 `.cmodel`。
- 错误时的失败上下文。

## 10. Golden Fixture 要求

### 10.1 标准参考模型

至少应包含：

- `校验模型.cmodel`：基础差速 AMR、陀螺仪、典型传感器、基础 IO。

- `ModelSet.cmodel`：舵轮 + 门架/升降 + 多 IO + 多传感器压力样例。

### 10.2 断言要求

每个 golden fixture 至少断言：

- 组件数量不变。
- UUID 集合不变。
- 主类型/子类型不被改写。
- 接口 UUID 集合不变。
- 接口类型集合不被改写。
- `linkedInterfaceUuid` 无悬挂。
- `AbiSet.componentAbility` 数量不变。
- `AbiSet.functionAbility` 数量不变。
- `FuncDesc.function` 数量不变。
- 空 `moduleDscType.typeKey`、空 `venderName.typeKey` 不被猜测填充。

### 10.3 异常模型样本

`proj*` 历史导出模型、缺失 `CompDesc` 的模型、protobuf 解析失败模型可作为异常样本。

用途：

- 验证错误诊断。
- 验证失败 artifacts 保留。
- 验证服务不会崩溃。
- 验证前端显示“不可导入/异常模型”状态。

不作为：

- 标准业务结构参考。
- 字段完整性基准。
- 模块库事实源。
