### 2.1 PR 自查清单（提交前逐项打勾）

```
□ 是否对照 Proto 定义列出了本次改动涉及 message 的全部字段？
□ 是否存在魔法数字/字符串？如有，是否已确认属于"工程规格常量"（如 FULL_LOAD_RATIOS）而非应从 schema 读取的值？
□ 新增/修改的 interface 是否使用 { key, source, required, fallback } 注册表模式？
□ COMBOX 类型是否严格通过 comboType.typeKey 定位选中分组，而非遍历取第一个匹配？
□ subSysType / moduleSys 取值是否落在 ENGINEERING_CONSTRAINTS.md §17 的白名单内？
□ 后端是否存在基于模块名称子串的类型推断？
□ 修改是否更新了 DATA_INTEGRITY_CONSTRAINTS.md 中的字段清单（如涉及 RobotIdentity）？
□ 修改是否影响 README / CLAUDE.md / CONSTRAINTS.md 中已写明的行为？若是，是否已在同一提交中同步？
□ 是否运行了 npm run build（零 tsc 错误）与相关 test:detailed？
```

## 3. 数据契约速记（不重复条文，只列"最容易忘"的几条）

- 接口属性数组字段必须是 `{ "interfaceParamsArray": [...] }`，禁止以 key 为索引的扁平 dict（ENGINEERING_CONSTRAINTS §19），因为 `ParseDict` 对非数组格式是**静默丢弃**，不会报错——这意味着这一类 bug 在开发阶段的手工测试中很容易被漏过，必须靠自动化 round-trip 测试兜底（见 §7）。
- 模块树落盘前必须完全扁平化（§20），`parentNodeUuid` 用 `DATA_COMBOX` 编码而非 `DATA_STRING`（2026-04-02 客户端已确认）。
- `moduleSys` 仅 `G_MainController` 保留，其余一律空字符串（§21）。
- privateAttrs 必须落在 Proto Tag 2，禁止被拍平进 `structParam.extendParams`（Tag 5，仅用于安装坐标与 `parentNodeUuid`）（§16）——2026-03-31 曾因此导致底盘参数（3组/33属性）整体丢失，是本仓库历史上最严重的一次数据丢失事故，任何触碰 `resource_adapter.py` 的 `is_chassis` 分支的改动都必须先重读该案例。
- DATA_FIXED_E 关联字段的值存于 `stringFix`（不是 `stringValue`），`"FIXED_RELATED_NONE"` 表示空引用，禁止用名称子串猜测归属（§13/§24.3）。

## 4. 前端代码规范

### 4.1 Schema 驱动渲染
禁止在 React 组件里硬编码物理组件的私有属性表；所有配置项（含边界、默认值、单位）必须经 `SchemaEngine.ts` 从 `ModuleLibrary` 按需加载（ENGINEERING_CONSTRAINTS §7）。若某型号存在不遵循基础 Schema 的互斥规则（下拉枚举条件隐藏等），只允许以 `ENGINEERING_CONSTRAINTS`（前端 `SchemaEngine.ts` 内的拦截器对象，与本规范文档同名但不同实体，注意区分）挂载，禁止污染 `ComponentPropertyPanel` 通用遍历逻辑。

### 4.2 CSS / 主题
禁止硬编码颜色值（`docs/INTERACTION_DESIGN_SPEC.md §4.1` 给出了完整黑名单与迁移映射表），一律使用 `var(--xxx)`。SVG 内部若因浏览器限制无法用 CSS 变量，须通过 `useSvgThemeColors()` 一类的主题探测 hook 集中管理，不得散落硬编码。

### 4.3 响应式
断点固定为 1200px（桌面）/768px（平板），关键容器使用 `flex: N` 比例而非固定像素宽度（`docs/INTERACTION_DESIGN_SPEC.md §1.2/§5`）。

### 4.4 状态管理
- 所有跨兄弟组件的参数联动（如双侧电机型号同步）必须通过 `syncAttributeToSiblings()` 一类的显式同步钩子实现，且同步判据应优先使用创建期注入的显式角色字段（如拟新增的 `functionalRole`），中文关键字子串匹配只能作为旧数据的 fallback，不得作为唯一判据（`design/implementation_plan.md` ISS-004 的教训）。
- 涉及深层嵌套属性的修改，前端应发送完整父分支（而非单个叶子字段），后端以 `deep_update` 处理，数组类型必须按 `key`/`type` 匹配合并而非整体覆盖（ENGINEERING_CONSTRAINTS §3）。

### 4.5 组件交互一致性
遵循 `docs/INTERACTION_DESIGN_SPEC.md §2` 的列表-详情模式规范（选中态左边框+发光、hover/active 0.2s 过渡、分组标题大写字母+11px），新增向导步骤 UI 时直接复用既有 `ListPanelSpec`/`EditorPanelSpec` 接口约束，不单独发明新的列表交互模式。

## 5. 后端代码规范

- **并发安全**：涉及 `encoder.py`（CPU 密集序列化）的 API 必须用同步 `def`，交由 FastAPI 线程池处理，禁止 `async def` 阻塞事件循环（ENGINEERING_CONSTRAINTS §4）。
- **递归安全**：`resolve_refs` 必须带 `visited` 集合防循环引用死循环。
- **项目隔离**：每个项目在 `saved_projects/{projectId}` 下必须有独立 `modules/` 目录及 `.bak` 备份，不得跨项目共享可写状态。
- **物理删除**：涉及 `rm` 的物理删除操作，必须先完成新成果物的 `AMR-CModel-Deep-Auditor` 校验并取得人工确认，禁止静默删除或自动清理非临时目录（ENGINEERING_CONSTRAINTS §12）——这一条同样适用于本次通过设备桥接对用户真实仓库做任何清理动作时，Claude 助手必须遵守。
- **审计日志**：每次导出必须返回 `audit` 日志，打印 `STEP2_COMPDESC_SERIALIZED` 等精确字节数；`deep_update` 必须打印 `DISK_CHANGE`；构建前执行 `deep_diff` 审计（ENGINEERING_CONSTRAINTS §5）。
- **错误契约**（本次新增，弥补既有文档空白）：所有面向前端的错误响应必须是结构化 JSON `{ "error": "<CODE>", "detail": "<human readable>", "node_path": "<optional>" }`，**禁止把 Python 异常的 `str(e)` 或 Worker 运行时堆栈直接透传给终端用户**（对应 `requirements/20260913_01` 的 REQ-EX-01，这是本次实操中复现率 100% 的问题，必须作为强制代码审查项，而不只是"建议"）。

## 6. 版本与提交规范

- **版本号**：遵循 SemVer（`主版本.次版本.修订号`），破坏性变更→主版本号，新增能力→次版本号，缺陷修复→修订号；必须与代码变更同一次提交，禁止版本号更新与功能提交分离（ENGINEERING_CONSTRAINTS §23）。同步更新 `pyproject.toml`/`package.json` 及 `CHANGELOG.md`。
- **文档编码**：所有 `.md`/配置文件必须 UTF-8 无 BOM，禁止 GBK/UTF-16/Latin-1（§8），否则 GitHub Actions/Jekyll 构建会报 `invalid byte sequence`。
- **README 同步**：任何代码框架变更、部署流程调整、接口协议变更必须在同一提交或任务闭环前同步更新 `README.md`（§8）。
- **隐私脱敏**：`README.md`/公开文档禁止出现真实姓名、联系方式、私有路径，贡献者一律用职能名或团队匿名（§8）。这一条对本次协作同样适用：本次提交的所有文档均已避免暴露用户真实操作系统路径与个人邮箱等信息，仅保留必要的仓库相对路径。
- **提交信息**：延续本仓库既有的 `类型(范围): 简述` 提交信息风格（参考 `docs(audits): 添加用户端全流程构建问题汇总与前后端优化方案`），中文简述 + 英文类型前缀（`feat`/`fix`/`docs`/`refactor`/`test`）。
- **分支策略**：文档类、审计类提交使用 `docs/<日期>-<主题>` 分支命名（延续本次已建立的 `docs/20260913-build-process-issues` 先例）；功能修复延续既有 `frontend-build-fix-<日期>`/`ts-backend-audit-<日期>` 命名风格。

## 7. 测试规范

- **字段完整性测试**：`tests/` 下的 `test:detailed` 必须与 `ExportService.ts` 中的 `ROBOT_IDENTITY_FIELDS` 保持同一份清单，禁止测试侧和实现侧各维护一份可能漂移的字段列表（DATA_INTEGRITY_CONSTRAINTS.md §2.1 步骤 2/3）。
- **Round-trip 测试**：任何触及 Import/Export/Encoder/Decoder 的改动，必须补充"编码→解码→再编码"三段式测试，断言字节级或字段级一致（PROTO_FIRST 工作流第 5 步；ENGINEERING_CONSTRAINTS §2 的"Proto 字段零省略"要求）。
- **浏览器端到端验证**：涉及向导交互的改动，建议使用 browser subagent 在本地 `http://localhost:3001/`（前端）+ `http://localhost:8002/`（后端）跑通目标场景的完整交互路径，而不仅是单元测试通过（`design/implementation_plan.md` "浏览器验证"章节的既有约定）。
- **回归优先级**：新增测试时优先覆盖《需求详细规格书》§6 追溯矩阵中标记为 P0 的条目（主控制器选型、驱动器 CAN 接口、编译按钮错误提示、虚拟列表可达性、输入框删除键、失焦持久化）。

## 8. 环境与本地开发

- 服务端口以 `8002`（后端）为 Ground Truth，前端固定 `3001`（ENGINEERING_CONSTRAINTS §6），生产环境（`amr.cloud-ai.work`）运行于 Cloudflare Workers（Frontend / Backend-worker-ts-edge），本地与生产的 `/compile` 行为应保持契约一致，禁止本地能跑通、生产因 Worker 特有限制（如未捕获异常处理方式不同）而不一致却无文档说明（对应 REQ-EX-01 的根因之一）。
- 本地启动统一走 `python3 start.py`（自动清理 8002/3001 端口冲突、健康检查），禁止另起临时启动脚本绕过该入口，避免出现"未重启导致 404"一类历史问题（`design/implementation_plan.md` ISS-010 教训）。
