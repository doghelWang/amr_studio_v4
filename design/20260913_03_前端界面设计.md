## 2. Schema 驱动渲染流程（沿用 `design/03_frontend_schema_logic_flow.md` 既有 mermaid 图，未发现需要修正之处，仅做索引）

关键路径：`ModuleLibrary PrivateAttribute.json`（Vite eager import）→ `SchemaEngine.buildAttributesFromSchema()` → `getEngineeringConstraints()`（拦截器覆盖默认值/隐藏非法枚举）→ `transformElement()` → `SmartAttribute[]` → `ComponentPropertyPanel`/`SmartForm` 渲染 → `onAttributeChange` → `syncAttributeToSiblings()` → 写回 `useProjectStore`。

轮组级联衍生（`doCreateWheel`，`PowerSystemStep.tsx`）：差速轮 `diffWheel` → 1 驱动器+1电机；差速舵轮 `diffSteerWheel` → 左右各1驱动器+1电机 + 1 外置绝对值编码器（角度反馈），与 `specifications/ENGINEERING_CONSTRAINTS.md §10` 的拓扑级联推导规则完全一致，本次实操中新增 4 组 `diffSteerWheel` 的实际行为符合该规则，唯独"轮组1轮间距默认值遗留为0"是该级联流程中的一个具体缺陷（见 §4.1）。

## 3. `ComponentLibraryStep.tsx` 目录逻辑（本次重点核实对象）

该组件维护 7 个"子步骤"（`subSteps`，对应"装备工坊"内的分类 Tab）：核心控制板 / 感知避障 / 电源管理 / 触点交互 / 信息显示 / 灯带氛围 / 其他扩展，每个子步骤内又有 `getSubCategories()` 定义的二级筛选（如核心控制板下的"主控制器/IO扩展板/通信模块"）。

**关键数据流**（实测代码，非既有文档转述）：`useEffect` 在组件挂载时请求 `GET ${backendBase}/api/v1/schemas`，将返回结果按 `sys`（系统分组）解析，对每个 entity 调用 `ImportService.mapEntityToComponent()` 得到 `category`/`mainModuleTypeKey`/`subModuleTypeKey`，存入 `libraryData`；而页面主列表 `filteredComponents` 实际过滤的是 `config.components`（**项目里已经添加的组件**），并非 `libraryData`。这意味着："组件库"页面主体展示的是"已装配清单"，`libraryData` 服务于"新增组件"弹窗（`isManualModalOpen`）。这一区分是本次代码分析的关键发现之一，解释了为何"主控与通信 0 items"最初被误判为"目录不存在"——用户在主列表看到的"0"其实是"尚未添加任何主控类组件"的正常初始态，真正的问题出在点击"新增"后，弹窗可选型号列表因 §4.1 所述的 Schema 收敛问题而**没有品牌型号可选**，只能选到两个通用占位类型。

## 4. UI 缺陷清单与修复设计（对应《需求详细规格书》§4/§5）

### 4.1 REQ-CL-01 前端改造点
`ComponentLibraryStep.tsx` 的"新增组件"弹窗（`isManualModalOpen` 分支）当前渲染逻辑推测仅消费 `subTypes`（通用类型），需要扩展为：选中 `MAIN` 二级筛选后，除展示 `subTypes` 外，同时展示后端新返回的 `brandedProducts[]`（《后端设计》§4.2）列表项，每项显示品牌型号名称，选中后：
1. 以该品牌型号的 `sourceFile` 对应模板创建组件（而非泛型 `subType` 默认模板）；
2. 立即以 `productId` 去掉前缀后的值查询 `board_desc`（现有 `boardInterfaces` 状态，来自 `GET /models/v4/BoardDescriptions.xml`），注入真实接口列表，复用 ISS-006 已有的注入时机逻辑，无需新建注入路径。

### 4.2 REQ-NF-04 虚拟滚动列表可达性（P0）
现象：Ant Design 虚拟化树/列表中，节点可能渲染在视口外数千像素处，标准"滚动到元素并点击"完全无法命中，只能通过 `element.scrollIntoView()` + `.click()` 的 JS 直接调用绕过。
修复设计：优先复核触发虚拟列表的容器高度计算是否在某些分支下取到了 0 或 NaN（虚拟滚动库通常依赖准确的容器尺寸测算高度表，尺寸计算错误是导致节点被定位到视口外的最常见原因）；建议在受影响的列表容器（`ComponentLibraryStep`/`PowerSystemStep` 中使用虚拟滚动的树组件）挂载后增加一次 `ResizeObserver` 驱动的高度重算，并在开发环境下对"节点数≥30"的场景补充一条 E2E 测试，断言可以通过键盘 `Tab`+`Enter`（不依赖鼠标滚动到位）选中列表末尾的节点。

### 4.3 REQ-NF-05 文本输入 Backspace/Delete 失效（P0）
现象：`芯片平台` 字段等文本输入中，删除键不生效但输入键正常，导致新旧文本拼接出"StepStepko"。
修复设计：优先排查该输入框是否为**受控组件但 `onChange` 处理器里对新值做了错误的字符串拼接**（例如错误地拼接了 `oldValue + newValue` 而非直接使用 `e.target.value`），这是受控输入框最常见的"删除键不生效"根因；同时检查是否有全局 `onKeyDown` 拦截器对 `Backspace`/`Delete` 做了 `preventDefault()` 但未正确转发到输入框的值变更逻辑。修复后必须补充"连续输入-删除-再输入"的交互测试用例，防止回归。

### 4.4 REQ-NF-06 ETH IP 失焦保存不一致（P0）
现象：Tab 键失焦后界面显示已保存，但刷新后字段变回空值；鼠标点击其他区域失焦则能正确持久化。
修复设计：审查该字段的 `onBlur` 处理器是否依赖 `relatedTarget`/`document.activeElement` 判断"是否已经离开表单区域"——Tab 键切焦与鼠标点击切焦在浏览器事件序列上存在差异（Tab 切焦时 `document.activeElement` 更新时机可能早于/晚于鼠标点击），若保存逻辑里有类似"仅当新的 activeElement 不在表单容器内才保存"的条件判断，Tab 键场景很容易被误判为"仍在表单内、无需保存"从而跳过持久化调用。修复方向为**不依赖失焦目标判断，只要 `onBlur` 触发就无条件发起保存 PATCH**（保存操作本身应是幂等的原子 PATCH，无条件触发不会引入额外风险）。

### 4.5 REQ-NF-07 电气连接页面层叠遮挡（P1）
现象：一旦点击过任意"功能装备栏"类目筛选，"模块库"选型面板会持续遮挡"电气连接"接线表单，刷新/重进步骤均无法自行恢复。
修复设计：怀疑是筛选状态对应的浮层组件（Modal/Drawer/Popover 之类）在关闭时只做了"视觉隐藏"（如 `visibility:hidden` 或 `opacity:0`）而未真正从 DOM 层级或 `z-index` 栈中移除，导致该浮层的层叠上下文一直"悬挂"在页面上。修复应确保筛选浮层关闭时组件被真正卸载（`unmount`）而非仅样式隐藏，或至少在卸载时显式重置其 `z-index`/`position` 相关的内联样式。

### 4.6 REQ-MT-01 "已定位/待定位"状态语义（P1）
现象：位置意图解算出全零坐标（如"中心"）时，即使点击保存，状态仍显示"待定位"。
修复设计：状态判定条件当前疑似为"坐标非零"，应改为"用户已显式确认过一次坐标（无论数值是否为零）"，即引入独立的 `isLocated: boolean` 标志位，由"保存"动作直接置位，与坐标数值是否为零解耦。

## 5. 交互设计规范遵循（沿用 `docs/INTERACTION_DESIGN_SPEC.md`，仅摘录与本次改造相关的硬性约束）

- 新增的"品牌型号选择"弹窗（§4.1）必须遵循既有 `ListPanelSpec`（48px 列表项高度、左边框选中态、hover 0.2s 过渡）与分类色点系统（`CATEGORY_SPEC`），不得另起视觉样式。
- 修复虚拟列表问题时不得为规避问题而放弃虚拟滚动、改为全量渲染——需求场景中组件数可达 39+，全量渲染会引入新的性能问题，正确方向是修复虚拟滚动的尺寸计算 bug（§4.2）。
